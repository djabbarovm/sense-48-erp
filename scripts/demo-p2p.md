# Demo: Purchase-to-Pay от заявки до сверки (C-10)

Сквозной прогон главного workflow на seed-данных: PR → согласование → приёмка →
счёт → платёж → batch → банк → RECONCILED. ~10 минут.

## Подготовка

```bash
./scripts/dev-db.sh start          # или docker compose up -d postgres
pnpm --filter @finance-os/db seed  # идемпотентен
pnpm --filter web dev              # http://localhost:3000
```

Пользователи (пароль у всех `Passw0rd!`, компания «Rooftop Hall»):

## 1. Заявка (Requester)

Войти как `chef@rooftop.test` → **Заявки на закупку → Новая заявка**:
«Лосось 30 кг», сумма `4 500 000`, RH-KITCHEN / FNB Food, vendor «Fresh Fruits Tashkent».
→ **Отправить на согласование**. Статус: На согласовании; бюджет-бейдж считается сразу (BR-014).

## 2. Согласование (Business owner + Finance)

- `chef@rooftop.test` → **Мои согласования** → слот BUSINESS_OWNER → Согласовать.
- `junior@fos.test` → карточка PR → слот FINANCE → Согласовать (Tier 1 по D-12; Tier 2+ добавил бы OWNER-слот).
- Статус PR: **Утверждена**. Каждый шаг виден в аудите внизу карточки.

## 3. Приёмка и счёт

- На карточке PR: **Создать PO** → **Приёмка FULL** (BR-042: для Tier 2+ приёмщик ≠ инициатор).
- **Счета и СФ**: у seed уже есть входящие СФ; импорт реестра Didox-формата — кнопка «Импорт» (xlsx).
  Дубликат СФ №118 лежит в статусе «Возможный дубликат» (BR-002) — разобрать кнопками.

## 4. Платёж с контролями (Junior)

`junior@fos.test` → **Платежи → Новый платёж**:
- Источник — счёт/PR/договор (без источника платёж невозможен, BR-001).
- **Проверить контроли** — до submit виден остаток к оплате (BR-010/011) и все контроли
  (BR-020 4-way match, BR-031 VERIFIED-счёт, BR-003 дубликат, BR-012 лимит договора, BR-023 документы…).
- **Создать и отправить** → READY_FOR_BATCH (все зелёные) или ON_HOLD (есть FAIL).

На «Платёжном столе» три колонки: **Готовы / Заблокированы / Ожидают документов**.
У заблокированных — код контроля, текст причины, кому эскалировать.
Exception (BR-050) может снять только Owner/Lead с указанием причины: войти как `lead@fos.test` —
на красной карточке появится форма «Exception».

## 5. Реестр (batch)

`junior@fos.test` → «Платёжный стол» → выбрать счёт «Трастбанк ****0101» → **Собрать batch**
(все READY попадают в сегодняшний OPEN-реестр; BR-051 — один STANDARD в день).
На карточке реестра:
1. **Freeze** (junior) — состав фиксируется, считается summary: сумма, cash после оплаты (BR-053),
   обязательства 7 дней, exceptions, related party (BR-036).
2. **Review** — только Lead и только не тот, кто делал freeze (4-eyes).
3. `owner@rooftop.test` → **Мои согласования**: batch-режим — summary-шапка, зелёные items списком,
   красные с toggle «Отклонить» + комментарий → **Approve all green**.
   BR-040: Owner не может утвердить платёж, который сам подготовил (SOD, 403).
4. **Экспорт CSV** — файл для Клиент-Банка (полный счёт получателя только здесь, BR-057), sha256 в аудите.
5. **Отправлен в банк** → items SENT_TO_BANK.

Готовый реестр для шага 3 уже есть в seed: **BATCH-2026-09-13** (REVIEWED, внутри related-party платёж).

## 6. Банк и сверка

`junior@fos.test` → **Банк и сверка**:
- Cash position по счетам (opening + транзакции).
- **Импорт выписки**: файл `packages/db/seed/bank/2026-09-12.csv` (Unified CSV)
  или реальная XLSX-выгрузка Трастбанк «Клиент-Банк». Повторный импорт ничего не дублирует (BR-056).
- Авто-матч (BR-055): ИНН+сумма+SENT → платёж становится **PAID** — это единственный путь в PAID,
  UI-кнопки нет, прямой UPDATE блокирует DB-триггер (BR-054).
- «Предложение» — принять вручную (выбор платежа) или Ignore с причиной.
- Отказ банка: секция «Отправлены в банк» → «Отклонён банком» + причина → FAILED + задача на пересоздание.
- Когда все платежи реестра PAID/FAILED — реестр сам становится **SETTLED**.

Предоплата (BR-022): после PAID у prepayment-платежа автоматически создаётся **Advance**
и задача CLOSING_DOCS с SLA в рабочих днях (видна у `doc@fos.test` в «Задачах»).

## 7. Что показать владельцу

- **Дашборд**: countdown до cutoff 14:00, квест дня, стрик без нарушений, «зелёный поток» %.
- **Аудит**: у любого объекта — полная история before/after; цепочка хешей проверяется `verifyAuditChain`.
- **Изоляция**: переключить компанию на Sense48 — данных Rooftop не видно (404, BR-073).
- Контроли нарушить нельзя: платёж без источника, дубль СФ, оплата сверх остатка,
  UNVERIFIED-счёт, самоутверждение — всё блокируется на уровне сервиса и БД.
