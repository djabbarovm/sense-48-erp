# ORDO Tower — ТЗ, дополнение №1

> Дополняет `22-ordo-tower-tz.md` (единый источник правды по контуру Tower). Не заменяет — добавляет требование к видам фонда. Приоритет — та же фаза, где делаются экраны здания/юнитов (2c+). Зафиксировано как ADR-044.

## Д1. Живое здание / шахматка / карточка юнита — что видно на юните

Виды фонда — **2.5D «живое здание», шахматка (этажи × юниты), план этажа** — общие для `BROKER` / `COMMERCIAL_DIRECTOR` / `CEO`. Цвет юнита = occupancy (заселено LTR / STR / свободно / ремонт / использует собственник / общая зона).

**По наведению/клику на юнит видно сразу (без открытия отдельной страницы):**
- статус занятости (заселён / свободен / ремонт / собственник);
- **ставка аренды и срок** — по какой цене и до какого числа снят юнит (start–end; пометка «истекает» при ≤ `lease_warn_days`); для продажи — цена и статус;
- текущий арендатор и коммерческий статус (показы / резерв / переговоры), если есть;
- для свободных юнитов — asking-ставка и дата, с которой доступен.

**Источник данных — хранимый `Contract` и `Listing`, НЕ rent-ledger.** Ставку и срок мы знаем из договора, который сами оформили (см. §6.3 основного ТЗ). При этом ongoing-аренду и дебиторку по LTR не ведём (см. §6.2). Срок из договора питает алерт «договор истекает» (§8).

**Смысл:** руководитель, глядя на здание или шахматку, за секунду видит коммерческую картину фонда — что занято, по какой цене и до какого срока, — не открывая каждый юнит.

## Acceptance
- На всех трёх видах фонда (2.5D, шахматка, план этажа) юнит показывает занятость цветом, а по наведению/клику — ставку, срок и арендатора из `Contract`.
- Данные берутся из `Contract`/`Listing`, отдельного rent-трекинга по LTR не появляется.
- Срок аренды из `Contract` корректно триггерит алерт «договор истекает».
