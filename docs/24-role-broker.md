# Профиль должности №2 — Брокер (`BROKER`, Азиз)

> **Статус:** источник истины по роли `BROKER`. Дополняет `docs/22-ordo-tower-tz.md` и `docs/23-role-call-center.md`.
> Интерим: 2 из 4 профилей (Камила/Мурад — далее). Реальность кода сверена с `docs/SYSTEM_MAP.md` — см. раздел **R**.
> **Не строить** новые сущности/миграции из этого профиля, пока не придёт полный набор. Гардрейлы: миграции с откатом; в `main` без полного диффа не вливать.

---

## 0. Роль и границы
Азиз — **брокер полного цикла**: от переданного Умаром лида до подписанного договора, фактической передачи помещения и полученной комиссии; и превращает объект собственника в позицию в фонде. **STR не трогает вообще** (механику STR проектируем отдельно позже). Два контура: сделка (спрос) и листинг (фонд).

## 1. Приём от Умара и ответственность после handoff
- Квалифицированные лиды и горячих собственников Умар передаёт **авто-передачей + Telegram push**.
- **После handoff ответственность полностью на Азизе:** дозвон, follow-up, показ, подбор, переговоры, документы, оплата, закрытие. Клиент перестал отвечать после handoff → это **follow-up Азиза, не повод вернуть лид**.
- **Return to qualification — только при проблеме первичной квалификации**, с типизированной причиной:
  - **QUALITY (возврат оправдан):** нет обязательных данных · неверная квалификация · неверная маршрутизация · невалидный контакт, который должны были проверить до handoff.
  - **НЕ вина Умара (не возвращать):** клиент перестал отвечать · изменил запрос · новая информация · сделка сорвалась позже · собственник передумал.
  - Возвраты QUALITY → метрика качества Умара.

## 2. Собственник по LTR / Sale — Азиз ведёт сам
После выявления и передачи собственника **Азиз самостоятельно ведёт коммерческую работу**; **Камила в обычную сделку не подключается**. Азиз: обсуждает объект · консультирует по рынку · согласовывает цену с собственником · организует подготовку · готовит листинг · ведёт входящий спрос · согласовывает офферы · закрывает. Owner master-data/история — в DMS, но активное взаимодействие по конкретному листингу — ответственность Азиза.

## 3. Ценообразование (исправление)
**Финальную цену/ставку определяет СОБСТВЕННИК.** Азиз: анализирует рынок · рекомендует · объясняет · может предлагать корректировку · **фиксирует согласованную с собственником цену в DMS**. **Камила обычную цену не утверждает; обязательного pricing-approval на каждую сделку нет.** Изменение цены хранит **историю:** предыдущая → новая · дата · кто инициировал · подтверждение собственника / комментарий.

## 4. Воронка сделки (спрос)
`NEW → QUALIFIED → PROPERTY_SELECTED → VIEWING → OFFER → NEGOTIATION → LOI → CONTRACT → MOVE_IN → WON | LOST`.
- **Показ назначает и проводит Азиз** (Умар — нет).
- **Оффер/переговоры:** клиент даёт другую цену → фиксирует offer → **связывается с собственником** → принято / отклонено / counter → в DMS. **Approval цены — от собственника, не от Камилы.**
- **Бронь/задаток:** Азиз вправе принимать. **Срок не хардкодить.** Reservation хранит: объект · клиент · сумма · дата · срок · условия · refundable/non-refundable/special · payment method · статус · next action · expiry. Приближение expiry → **alert**. Продление/снятие — с историей.
- **Проверка (DUE_DILIGENCE):** аренда — арендатор; продажа — юр. чистота, кадастр, финансирование.
- **`BROKER_STAGE_LIMIT` — расхождение кода с моделью.** Азиз — полного цикла. State machine пока не ломать; при delta: разрешить брокеру `CONTRACT`/`MOVE_IN`; **WON не ставить вручную** — только из подтверждённого события (`activateLease` / `closeSale`).

## 5. Sale / Resale — до нотариуса
Азиз ведёт продажу до нотариуса и завершения. Нотариус/регистрация — внешние шаги, но их **статус в его deal journey**. Ориентир (уточним при review, машину раньше времени не ломать):
`NEGOTIATION → AGREED → DUE DILIGENCE → CONTRACT/AGREEMENT → NOTARY SCHEDULED → NOTARY COMPLETED → SETTLEMENT → OWNERSHIP TRANSFER CONFIRMED → WON`.

## 6. Листинг + Marketing handoff
Азиз отвечает за готовность объекта к продаже/аренде. Проф. съёмку/рекламу делает **Marketing** через handoff:
`OBJECT READY FOR MEDIA → задача Marketing → photo/video → материалы загружены → listing assets готовы → возврат Азизу → MARKET READY / PUBLISHED`.
Связь: **Unit ↔ Listing ↔ Media package ↔ Marketing task**. Полную OM Marketing не строим — только handoff.

## 7. Договор — по шаблону, структурированные данные
Стандартные сделки — **по шаблону; Азиз не пишет договор с нуля**. Flow: `approved deal data → DMS подставляет стороны/объект/суммы/сроки → генерирует по шаблону → Азиз проверяет → подписывается → финальная версия в DMS`.
Хранить **структурированные данные сторон, не только PDF:** ФИО · контакты · реквизиты · паспортные/идентификационные данные · данные объекта · сроки · цена/ставка · депозит · условия.
**Паспортные/идентификационные документы — защищённые, ограниченный доступ + аудит**, не публичные поля карточки. Нужно для Operations / Services / Contracts / повторных сделок.

## 8. Handover / Move-in
Азиз фиксирует фактическую передачу: **акт приёма-передачи · фото/видео состояния · показания счётчиков · количество ключей · карты доступа · переданные предметы · дата фактической передачи**.
Различать: **A. Marketing media** (проф. фото для листинга — Marketing) vs **B. Handover evidence** (фото состояния, счётчики, ключи — **Азиз**).

## 9. Definition of Done сделки LTR / Office
Не заканчивается на подписании. Journey завершён только когда: договор подписан → оплата выполнена / follow-up закрыт → фактическая передача → акт + фото + счётчики + ключи/карты → заселён / передан → клиент познакомлен с Services → данные переданы дальше.

## 10. Services handoff
После LTR/Office Азиз знакомит клиента с Services (полную OM Services не строим). Минимум: Contact · Unit · Contract · move-in date · контакты · доступы/ключи/карты · service needs · история передачи.

## 11. Деньги — роль Азиза
- Комиссия **ACCRUED при закрытии** (авто), сумму руками не задаёт.
- **Наличные (Cash SLA сейчас не нужен):** клиент → Азиз получил cash → **DMS фиксирует custody у Азиза** → передал Камиле → Камила сдала в кассу → **после подтверждения → PAID**. **Азиз сам PAID не ставит.** На экране — «**Наличные к передаче**» с суммой и сделками.
- **Безнал:** Азиз ведёт **follow-up до фактического поступления**, видит статус: `ожидается · напомнили · обещал · платёж отправлен · поступление подтверждено`. Финансовый факт подтверждает **bank/finance контур**. **PAID не ставит.**
- **Внешний брокер:** фиксирует участие и условия, но **split/комиссию утверждает Камила** (отдельный approval).

## 12. Что Азиз видит по деньгам
**НЕ видит** внутреннюю экономику комиссии ORDO и финаналитику сделки. **Видит:** статус оплаты клиентом · cash custody · **свой** бонус и его статус.

## 13. Экран и раскладка
- **По умолчанию:** «Мой день» / «Доска сделок» (канбан).
- **Всегда на виду:** показы сегодня · новые лиды (от Умара) · сделки без шага · резервы истекают · **наличные к передаче** · безнал в follow-up.
- **Рабочая зона:** канбан; карточка — клиент, объект, этап, next action, **документы (договор/акт/фото/счётчики/ключи)**, кнопки этапа. Живое здание/юниты (ставка/срок/арендатор — Доп.№1), листинг.
- **Частые действия:** Назначить показ · Подготовить оффер (согласовать с собственником) · Двинуть этап · Сгенерировать договор по шаблону · Зафиксировать handover · Принять cash → передать Камиле · Задача в Marketing.

## 14. День · События
Утро — «Мой день»: показы, новые лиды, сделки без шага, истекающие резервы, наличные к передаче. День — показы, движение сделок, оферы (с собственником), договоры+акт+фото, приём/передача cash, онбординг. События: лид передан → принять/вернуть (QUALITY) · показ · оффер клиента → к собственнику · резерв истекает → продлить/снять · договор истекает → ротация · объект готов к съёмке → Marketing.

## 15. Выход и критерий «сделано»
= Definition of Done (§9). Для листинга — объект MARKET READY / PUBLISHED.

## 16. KPI
**Главный — закрытые сделки.** Доп.: conversion handoff→showing · showing→offer · offer→deal · lead→close time · число закрытых · объектов до market-ready · скорость подготовки листинга · next-action discipline · payment follow-up · cash custody · полнота contract/handover package · фактический move-in · собственный бонус. **STR не включать.**

## 17. Права в системе (по реальной матрице)
- `deal.view/manage`, `deal.contact.view` (свои), `lease.view/manage`, `unit.publish`, `bonus.own`.
- **Нет:** `rent.view`, `unit.pricing.edit` *(цену ставит собственник — реконсиляция R2)*, `commission.manage`, `rent.match`, `owner.activity`, `mall.manage`, `bonus.confirm_kpi/pay`.
- Row-level: только **свои** сделки (`brokerOnly`, чужая = 404).

## 18. Чего НЕ делает
Не подтверждает свою комиссию/её оплату (Камила) · не ставит PAID (cash — Камила, безнал — финансы) · не решает split внешнему брокеру (Камила) · не ведёт owner-relationship пайплайн/обзвон (Умар/Камила) · не делает проф. съёмку (Marketing) · не трогает STR/управление/пул/ТРЦ.

## 19. Управление · Team scale
Руководитель — **Камила**. Система на **несколько брокеров** (не на одного): Камила распределяет лиды/собственников/объекты/сделки и видит workload (active leads/deals, showings, hot deals, overdue, listings in prep, closed). Метрики Азиза питают её пульт.

## 20. Геймификация · Состояния
Геймификация — **события сейчас, UI позже**; награда за подтверждаемый результат (закрытая сделка, собранная комиссия, полный пакет), не за активность. Состояния: нет показов · сделки без шага · резерв/договор истекает · противоречие в юните · наличные к передаче · безнал завис · возврат · ошибка загрузки · пустая доска.

## R. Реконсиляция с кодом (проверено — деструктивно сейчас НЕ переделывать)

### R1. Полный цикл vs `BROKER_STAGE_LIMIT` — **КОНФЛИКТ** (держать долг)
- **Профиль (§0, §4):** Азиз ведёт до `CONTRACT`/`MOVE_IN` и закрытия.
- **Код:** `BROKER_MAX_STAGE = 'LOI'` (`packages/core/src/property/deal.ts:25`); guard `BROKER_STAGE_LIMIT` (deal.ts:56) блокирует `brokerOnly` выше LOI, а `win`-триггер для `brokerOnly` вообще запрещён (deal.ts:70). Т.е. сегодня `BROKER` **не может** сам довести сделку до `CONTRACT`/`MOVE_IN` — это делает менеджер/директор.
- **Вывод:** по модели поднять `BROKER_MAX_STAGE` до `MOVE_IN` (или снять для brokerOnly ограничение на договорные стадии), сохранив **WON только из события**. `WON вручную` уже невозможен в коде (win не через advance) — это **совпадает** с профилем. Менять лимит **позже**, вместе с M3 и профилем Камилы; тесты `property.test.ts`/`property-wave2.test.ts`/`deals.spec.ts` завязаны на текущий лимит — не рвать сейчас.

### R2. Цену определяет собственник, история цены — **КОНФЛИКТ прав + НЕ ПОСТРОЕНО**
- **Профиль (§3):** финальную цену ставит собственник; Азиз фиксирует её в DMS; Камила обычную цену не утверждает; изменение цены хранит историю.
- **Код:** `unit.pricing.edit` = OWNER/COMMERCIAL_MANAGER/COMMERCIAL_DIRECTOR (`matrix.ts:104`) — у `BROKER` **нет**. Цена живёт на `Unit` (`askingRateMinor`/`minApprovedRateMinor`/`salePriceMinor`) и `Deal` (`expectedRateMinor`/`commissionRateBp`/`salePriceMinor`). **Истории цены (было→стало, кто, подтверждение собственника) в коде нет.**
- **Вывод:** развилка — либо дать брокеру фиксировать owner-agreed цену (доп. право/поле «согласовано собственником»), либо оставить запись цены за менеджером. Нужен объект/лог истории цены. Решать при полном наборе профилей; сейчас **не менять** матрицу и зеркалирование.

### R3. Деньги: cash-custody и «Азиз не ставит PAID» — **частично совпадает, cash НЕ ПОСТРОЕН**
- **Совпадает:** Азиз PAID не ставит — `matchCommissionReceipt` требует `rent.match` (финансы), у брокера его нет; комиссия ACCRUED авто при закрытии (`accrueCommission`); сумму брокер не задаёт. Это уже так в коде.
- **НЕ ПОСТРОЕНО:** cash-путь (custody у Азиза → передача Камиле → касса → подтверждение = PAID), экран «наличные к передаче», безнал-follow-up статусы. Это Phase 3 (два пути settlement BANK + CASH). **Существующий bank-match не ломать.**

### R4. Reservation — **ТОНКО** (поля есть, объекта нет)
- **Код:** `Deal.reservedUntil` + `Deal.depositReceived` есть; полноценного Reservation с суммой/условиями/refundable/payment method/историей/expiry-alert **нет**.
- **Вывод:** гибкий срок брони (не хардкод), история и alert — строить позже; срок брать из `tower_setting` (`reserve_hours`, уже есть дефолт).

### R5. Договор по шаблону + структурированные стороны + защищённые паспортные — **НЕ ПОСТРОЕНО**
- **Код:** есть `Document`/`DocType` (доки) и `LeaseContract` (сделочные поля), но **нет** генерации по шаблону, структурированных данных сторон и защищённого класса паспортных документов с доступом/аудитом.
- **Вывод:** пересекается с §6.3 ТЗ (Contract + пакет документов, Phase 3). Паспортные — как защищённые с ограниченным доступом + аудит (у нас уже есть `withAudit` и PII-исключения — переиспользовать).

### R6. Handover evidence — **НЕ ПОСТРОЕНО**
Акт/фото состояния/счётчики/ключи/карты/дата передачи — сущности нет. `UnitActivity` пишет заметки, но структурированного handover-пакета нет. Строить в Phase 3 (§6.3). Отделять от Marketing media (R7).

### R7. Marketing handoff / Listing / Media — **НЕ ПОСТРОЕНО**
Отдельной `Listing`-сущности и Media package нет (публикация = `Unit.publishedAt`). WorkOrder/ServiceOrder — про эксплуатацию/услуги, не про медиа-производство. Связь Unit↔Listing↔Media↔Task — строить позже; сейчас только предусмотреть handoff, полную OM Marketing не делать.

### R8. Sale journey до нотариуса — **НЕ ПОСТРОЕНО**
`DealStage` не содержит `AGREED/NOTARY_*/SETTLEMENT/OWNERSHIP_TRANSFER`. Расширять enum sale-специфичными статусами — отдельное решение (миграция), не сейчас; общую машину раньше времени не ломать.

### R9. Return-to-qualification (typed) — **НЕ ПОСТРОЕНО** (связка с профилем №1 R3)
Возврата с типизированной причиной и метрикой качества Умара в коде нет. Строить вместе с handoff-механикой КЦ.

### R10. Права `BROKER` — **СОВПАДАЕТ** (проверено по `matrix.ts`)
Есть: `deal.view`, `deal.manage`, `deal.contact.view`, `lease.view`, `lease.manage`, `unit.publish`, `bonus.own`, плюс `property.view`, `unit.status.commercial`, `unit.activity.create`, `deal.checklist`, `workorder.*`/`service.*` (create/view), `action.draft`, `owner.pipeline` (view). Нет: `rent.view`, `unit.pricing.edit`, `commission.manage`, `rent.match`, `owner.activity`, `mall.manage`, `bonus.confirm_kpi`, `bonus.pay`. Row-level `brokerOnly` (чужая сделка = 404) — есть (`loadOwnDeal`). Соответствует §17/§18. **Нюанс:** `owner.activity` у брокера нет (докс/21 §4), т.е. §2 «Азиз ведёт собственника» реализуется через **сделку/листинг**, а не через owner-activity — учесть в UX.

### R11. Внешний брокер split — **данные есть, approval-гейт НЕ ПОСТРОЕН**
`Deal.externalBrokerName`/`externalShareBp` есть; `Commission.netMinor` вычитает долю внешнего брокера. Но **отдельного утверждения split Камилой** (approval-действие) нет — сейчас это просто поля. Добавить approval позже (профиль Камилы).
