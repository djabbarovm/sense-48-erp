## ADR-001: Prisma 6 вместо Prisma 5
**Дата:** 2026-09-14 · **Фаза/задача:** A-01/A-03
**Контекст:** D-02 фиксирует «Prisma 5 + PostgreSQL 16». Prisma 5 — устаревшая major-версия; Prisma 6 — текущая стабильная с тем же API уровня schema/client и лучшей поддержкой Node 22.
**Решение:** Использовать Prisma 6.x. Schema-синтаксис и клиентский API совместимы с D-02 по существу (декларативная schema, миграции, PostgreSQL 16).
**Последствия:** Нет известных потерь функциональности; при возврате на 5.x достаточно даунгрейда зависимости.

## ADR-002: Dev-auth — собственный JWT-мок с интерфейсом под Supabase
**Дата:** 2026-09-14 · **Фаза/задача:** A-02/A-05
**Контекст:** D-03 требует Supabase Auth; A-02 допускает «supabase-auth или packages/auth-mock с JWT для dev — решить и записать ADR». Полный self-hosted Supabase (GoTrue+Kong+Studio) тяжёл для dev/CI и не добавляет ценности до продакшена.
**Решение:** Реализовать `AuthProvider` interface в core (verifyToken → {userId, email}) с двумя реализациями: `DevJwtAuthProvider` (HS256, секрет `AUTH_JWT_SECRET`, форма claims совместима с Supabase: `sub`, `email`) и заготовка `SupabaseAuthProvider` (проверка JWT Supabase по JWKS/секрету) для продакшена. Email+password логин в dev — против таблицы `User` с bcrypt-хэшем (только dev-пароли из seed). MFA-поля моделируются (`mfa_enabled`), enforcement — на уровне политики ролей.
**Последствия:** Переход на реальный Supabase = замена провайдера + миграция пользователей; RBAC и TenantContext не меняются, т.к. живут в собственных таблицах (D-03).

## ADR-003: Тестовая БД — локальный PostgreSQL, docker compose — канонический dev-контур
**Дата:** 2026-09-14 · **Фаза/задача:** A-02
**Контекст:** Разработка идёт в песочнице, где docker-демон может быть недоступен/медленен, а PostgreSQL 16 установлен нативно.
**Решение:** `docker-compose.yml` — канонический способ поднять dev-инфраструктуру (postgres, redis, minio, mailhog). Для интеграционных тестов и песочниц добавлен `scripts/dev-db.sh`, запускающий локальный кластер PostgreSQL 16 (initdb в `/var/lib/finance-os-pg`, trust auth, только localhost). Тесты берут `DATABASE_URL` из env и не зависят от способа запуска БД.
**Последствия:** Один и тот же тестовый код работает в compose-окружении и в песочнице. Trust-auth допустим только для localhost dev; в prod — только пароль/TLS.

## ADR-005: StorageAdapter c LocalFs-fallback для dev
**Дата:** 2026-09-14 · **Фаза/задача:** B-09
**Контекст:** D-04 требует S3-совместимое хранилище (MinIO в compose). В песочнице/CI MinIO может быть недоступен.
**Решение:** `StorageAdapter` interface в packages/adapters: `S3Storage` (aws-sdk v3, forcePathStyle для MinIO, signed URL 15 мин) — прод/dev c compose; `LocalFsStorage` — фолбэк для песочниц и юнит-тестов (`createStorageFromEnv` выбирает по env S3_*). Метаданные, sha256 и версии — всегда в таблице Document.
**Последствия:** Тесты не требуют MinIO; смена бэкенда хранения не трогает домен.

## ADR-006: Кто закрывает событие при BR-061 override
**Дата:** 2026-09-14 · **Фаза/задача:** D-03
**Контекст:** docs/05 даёт `event.close` только FINANCE_OPS_LEAD, а BR-061 разрешает закрытие с блокерами «Owner с reason». Owner формально не имеет `event.close`.
**Решение:** Обычное закрытие (без блокеров) — только Lead. Owner допускается к триггеру close исключительно как носитель override: guard BR-061 пропускает блокеры только при `isOwner && reason`. Матрица прав не расширяется.
**Последствия:** Lead не может закрыть событие с блокерами даже с reason (эскалация Owner'у); аудит фиксирует reason в `event.close`.

## ADR-007: Telegram-уведомления — HTTP-адаптер + mock вместо grammY-бота в dev
**Дата:** 2026-09-14 · **Фаза/задача:** D-06
**Контекст:** docs/07 §5 описывает grammY-бот c линковкой chat_id через `/start <code>`. CLAUDE.md фиксирует: реальных API в разработке нет, все внешние системы — adapter interfaces + mock.
**Решение:** В packages/adapters: `NotificationAdapter` interface + тексты шаблонов (без сумм и контрагентов), `MockNotificationAdapter` (тесты), `ConsoleNotificationAdapter` (dev), `TelegramNotificationAdapter` (HTTP Bot API, токен из env, chat_id через резолвер → User.telegramChatId), `EmailNotificationAdapter` (инжектируемый SMTP-транспорт → MailHog/nodemailer) и `FallbackNotificationAdapter` (Telegram → email). Долгоживущий bot-процесс c `/start`-линковкой и командами `/help`/`/mute` подключается при внедрении на сервере клиента.
**Последствия:** Джобы и сервисы не знают о канале доставки; включение реального бота — конфигурация, не код. BR-072 соблюдён на уровне шаблонов (в параметрах нет сумм).

## ADR-008: Исторические оплаты при миграции — служебные платежи через архивный счёт
**Дата:** 2026-09-14 · **Фаза/задача:** E-05
**Контекст:** open_ap.xlsx несёт `paid_to_date`, но BR-054 (DB-триггер) запрещает PAID/CLOSED-платёж без банковской транзакции, а Invoice не хранит «оплачено».
**Решение:** Импортёр создаёт счёт на полную сумму (номер сохраняется для дедупликации BR-002 и сверки актов), а `paid_to_date` проводит служебным PaymentRequest в статусе CLOSED, привязанным к синтетической транзакции на архивном банковском счёте «Миграция» (`is_active=false`). Балансы/aging считаются штатной логикой; cash position и forecast архивный счёт не видят.
**Последствия:** BR-054 не ослабляется даже для миграции; исторические оплаты видны в аудите и в 360-карточках. Поле `due_date` из шаблона игнорируется (срок считается из даты СФ + условий договора) — колонка оставлена для совместимости выгрузок.

## ADR-009: Обмен c 1С — CSV-проводки + платёжки 1CClientBankExchange, счета по НСБУ-21
**Дата:** 2026-09-14 · **Фаза/задача:** E-04
**Контекст:** docs/07 §4 задаёт CSV-экспорт постингов; реального API 1С нет. Ресёрч показал: де-факто стандарт «Обмен c системами Клиент банка» (1CClientBankExchange, Windows-1251) принимают и банки, и 1С; план счетов РУз — НСБУ №21 (1010/2910/9410/9420/0820, НДС 4410, поставщики 6010, авансы 4310, подотчёт 4220/4230, зарплата 6710, бюджет 6410, МФО вместо БИК).
**Решение:** Три потока: (1) платёжки утверждённого батча — файл 1CClientBankExchange (builder в adapters, cp1251 через iconv-lite) — грузится и в Клиент-Банк, и в 1С; (2) проводки месяца — CSV по docs/07 c account_code из AccountMapping (стартовый сид по НСБУ-21, правится в админке); (3) подтверждение — posted.csv → CLOSED + onec_ref. Руководство для бухгалтера — docs/13-onec-guide.md.
**Последствия:** Внедрение не требует доработок на стороне 1С в день один (типовые механизмы загрузки); субсчета уточняет бухгалтер в маппинге, код не меняется.

## ADR-011: Импорт управленческой книги KSP + касса как счёт CASH
**Дата:** 2026-09-15 · **Фаза/задача:** H-01
**Контекст:** Текущий учёт Rooftop ведётся в Excel-книге KSP Consulting (39 листов: банк-журнал, касса, балансы контрагентов, реализация, маппинг выписки). Для запуска на реальных данных нужен стартовый срез. Владелец решил не заполнять шаблоны, а грузить реальные выгрузки как есть.
**Решение:** (1) Одноразовый импортёр книги: парсер в `adapters/ksp` (индексы колонок — из строк заголовков, т.к. SheetJS отбрасывает пустые ведущие столбцы; колонка «ИТОГО» в книге битая — сальдо считаем как «Авансы + Задолженность»), сервис `importKspBook` — идемпотентный, всё в одной withAudit-транзакции. (2) Открытые сальдо — сводные документы `САЛЬДО-KSP-<дата>` (AP: invoice type ACT; AR: customer_invoice), переплаты/авансы в документы не превращаются — возвращаются отчётом на ручной разбор. (3) ИНН в книге нет → заглушка `KSP-nnnn`, статус PENDING_VERIFICATION: платежи на таких поставщиков заблокированы до прихода реквизитов из 1С (совместимо с BR-030). (4) Наличные — отдельный BankAccount «Касса» (accountMasked=КАССА): операции книги грузятся транзакциями, до 01.09.2026 — IGNORED (разобраны вне системы), позже — UNMATCHED в текущую сверку. (5) Историю расчётного счёта из книги НЕ грузим — источник банковских транзакций только выписка банка (BR-054/056), иначе двойной учёт. (6) Правила листа «Маппинг» — новая модель CounterpartyMatchRule (unique tenant+pattern) для будущего автоподбора контрагента при разборе выписки.
**Последствия:** Реальный тенант `rooftop-real` отделён от демо `rooftop`; сам файл книги в репозиторий не коммитится (реальные данные). После выгрузки из 1С заглушки ИНН заменяются реальными (H-02), сальдо сверяются с ОСВ 6010/4310/4010.

## ADR-012: Ролевая модель пилота PALYM — 4 профиля на 7 системных ролей
**Дата:** 2026-09-15 · **Фаза/задача:** H-05
**Контекст:** Реальная команда пилота: 1 финансовый менеджер, 1 бухгалтер, 1 закупщик и руководители/учредители, которым нужен дашборд и управленческая отчётность. Владелец предложил «один профиль на руководителей».
**Решение:** Код и матрица прав не меняются — маппинг: закупщик → REQUESTER; финансовый менеджер → FINANCE_OPS_LEAD (+ADMIN второй ролью для настроек); бухгалтер → ACCOUNTANT (принимает на себя функции DOCUMENT_CONTROLLER — контроль закрывающих и СФ); руководители/учредители → OWNER, при этом ЛОГИН У КАЖДОГО СВОЙ: общий аккаунт ломает аудит (не видно, кто одобрил) и four-eyes (BR-003). Роли DOCUMENT_CONTROLLER и JUNIOR_FINANCE в пилоте не выдаются. Цепочка контролей на малой команде: закупщик подаёт → финменеджер финансовый слот/платёж → OWNER одобряет батч → бухгалтер сверяет и закрывает в 1С.
**Последствия:** Учётки создаются по списку «ФИО-email-профиль» от владельца (H-05). Управленческая отчётность учредителей: Owner Dashboard + Портфель + month-end pack; после загрузки выписок — владельческий P&L в разрезах книги KSP (статьи/группы P&L), чтобы переход от KSP-отчётности был бесшовным.

## ADR-013: CEO-контур строится вокруг «Пути CEO» владельца (docs/15)
**Дата:** 2026-09-15 · **Фаза/задача:** H-07
**Контекст:** Мои макеты (пульт и утренняя сводка) шли от учётных данных. Владелец сформулировал путь от бизнес-вопросов: зарабатываем/отстаём, точка безубыточности по бизнесам, загрузка Rooftop и Sense, где нужен CEO. Два окна: «Утро» (положение и приоритеты) и «Сегодня» (только изменения и исключения).
**Решение:** docs/15-ceo-path.md — источник истины CEO-контура. Ключевые следствия для модели: (1) BusinessUnit (Rooftop / Sense 48) как разрез всех CEO-метрик независимо от юр. структуры (юрлица уточняются отдельно и влияют только на платёжный контур/тенанты); (2) новые справочники: фиксированные расходы месяца по бизнесам, типовые нормативы себестоимости по форматам, календарь продаваемых дат; (3) модуль Event расширяется до мини-CRM (предварительная бронь → подтверждено, готовность, главный риск, ответственный); (4) Sense требует источника данных о визитах/загрузке — интеграция c системой записи или ручная дневная сводка; (5) «Итог одной строкой» генерируется детерминированными правилами (без магии), правила фиксируются в core c тестами.
**Последствия:** прежние макеты остаются уровнем детализации под «Утром». Реализация поэтапно: справочники → «Утро» v1 (break-even Rooftop, загрузка дат, ближайшее событие, деньги, решения) → Sense-блок → «Сегодня» + событийные алерты в Telegram.

## ADR-014: ТЗ CEO-дашборда (docs/16) — источники истины и порядок интеграций
**Дата:** 2026-09-15 · **Фаза/задача:** H-08
**Контекст:** Владелец зафиксировал формальное ТЗ (docs/16-ceo-dashboard-tz.md): продажи Rooftop живут в amoCRM (новый источник, ранее события велись в Finance OS), Sense — Altegio + iiko, финансы — банк/1С. Требуется единый источник на показатель и отсутствие двойного ввода.
**Решение — таблица источников истины:**
сделки/воронка/календарь Rooftop → amoCRM (Event в FOS становится зеркалом сделки, поле amoDealId); визиты/загрузка Sense → Altegio; чеки/F&B/себестоимость → iiko; факт денег → банковская выписка (как и было, BR-054), 1С — официальный учёт и сверка; управленческие расчёты (БУ, прогноз, решения, бонусы, экономика мероприятия) → Finance OS.
**Направление синхронизации v1: только внешняя система → Finance OS.** Пункт 16 ТЗ (правка даты из FOS обратно в amoCRM) отложен: двусторонняя запись противоречит принципу №1 того же ТЗ («данные вводятся один раз в профильной системе») и опасна конфликтами; в v1 дата меняется в amoCRM и приезжает к нам. Вернёмся после стабилизации односторонней синхронизации.
**Порядок интеграций v1:** (1) amoCRM — сердце дашборда (сделки, календарь, категории выручки потенциальная/ожидаемая/подтверждённая); (2) Altegio; (3) iiko; (4) 1С-обмен уже есть (E-04). До получения доступов блоки работают на текущих модулях (Event вручную, SenseDailyStat) и честно помечаются источником.
**Также:** «Нет данных» ≠ 0 — вводится мета-слой свежести (источник + updated_at на показателе); решения CEO становятся сущностью c действиями (согласовать/отклонить/делегировать/запросить инфо/срок/комментарий) и аудитом; условия автоподтверждения мероприятия (п.15) реализуются поверх BR-062; бонусы продажников — после утверждения положения (вопрос 14 ТЗ).
**Последствия:** блокирующие вопросы для старта интеграций — доступ и структура amoCRM (вопросы 2–5), API-ключ Altegio (6), расходы/нормативы/планы выручки (11–13), минимальный депозит и пороги решений (9, 15).

## ADR-015: Правообладатель продукта — физическое лицо c последующей передачей в компанию
**Дата:** 2026-09-18 · **Фаза/задача:** IP-01
**Контекст:** Продукт разрабатывается одним владельцем; юридическое лицо ещё не зарегистрировано. Нужно, чтобы всё созданное c этого момента было документально закреплено за владельцем и могло быть чисто передано компании. Дополнительно: 37 из 50 коммитов подписаны обезличенным аккаунтом инструмента, а в репозитории лежат данные клиента PALYM (книга KSP, учётки команды).
**Решение:** (1) Правообладатель — Murad Djabbarov как физическое лицо; режим лицензирования проприетарный (`LICENSE`, `package.json.license = UNLICENSED`). (2) Состав продукта, состав исключений (данные клиента, секреты, сторонние библиотеки) и схема передачи в компанию зафиксированы в `docs/17-ip-ownership.md`; там же ведётся реестр задач юристу. (3) Все последующие коммиты подписываются именем и почтой правообладателя; история до 18.09.2026 не переписывается — она доказательство хронологии, а авторство закрепляется через спецификацию, ADR и приёмку задач. (4) Ядро продукта не содержит знаний о конкретном клиенте; клиентское — только в тенанте, зашифрованных файлах и секретах. (5) Copyleft-зависимости (GPL/AGPL) — только через отдельный ADR.
**Последствия:** передача в компанию — договор об отчуждении или вклад в уставный капитал (решает юрист), фиксируется коммитом + тегом `ip-transfer-*`. Клиентские договоры до передачи — от физлица либо c уступкой. Любое изменение состава продукта отражается в docs/17 в том же коммите.

## ADR-016: Продукт называется MDS; MDS Property строится в этом монорепо как второй модуль владельца
**Дата:** 2026-09-18 · **Фаза/задача:** P-01
**Контекст:** Владелец начинает второй продукт по blueprint «Piramit Digital Platform» (управление недвижимостью: Property Core, Живое здание, CRM, Owner Portal, WorkBot). Имя партнёрской управляющей компании в названии продукта использовать нельзя: продукт должен принадлежать владельцу на 100%, а управляющая компания и объект Piramit — клиенты. Отдельный репозиторий дал бы чистую границу, но потребовал бы заново собрать RBAC, audit, tenant isolation, i18n, CI и деплой, которые в Finance OS уже готовы и покрыты тестами.
**Решение:** (1) Бренд продукта — **MDS** (инициалы владельца); Finance OS остаётся именем финансового модуля, новый модуль — **MDS Property**. (2) MDS Property живёт в этом монорепо: домен — `packages/core/src/property`, сервисы — `packages/db/src/services/property.ts`, экраны — `apps/web/app/(app)/property`. Общая платформа (tenant, users, roles, audit, i18n, CI) переиспользуется. (3) Первый тенант — `piramit` (seed синтетический); ни в коде, ни в именах пакетов имя клиента или управляющей компании не фигурирует. (4) Переименование workspace-scope `@finance-os/*` и репозитория `sense-48-erp` в нейтральное имя — отдельная задача владельца (P-09), git-история при этом сохраняется.
**Последствия:** docs/17 (реестр ИС) распространяется на оба модуля без изменений; LICENSE упоминает MDS. Клиентские данные (PALYM, Piramit) остаются только в тенантах. Выделение общих пакетов (`@mds/platform`) — когда появится третий модуль или второй репозиторий.

## ADR-017: Статусная модель юнита — шесть нормализованных полей, цвет вычисляется, договор в v1 — поля юнита

## ADR-018: Wave 2 MDS Property — LeaseContract и Deal как сущности, юнит остаётся зеркалом
**Дата:** 2026-09-18 · **Фаза/задача:** P-10
**Контекст:** В v1 договор аренды и стадия сделки — поля юнита (ADR-017). Blueprint §6 требует CRM-воронку c источниками/UTM и категориями выручки, §1.10 — contract/deal как сущности c историей, §1.11 — событие `unit.status.changed` и API для сайта/бота. Отдельный Contract (P2P, docs/04) — договор c поставщиком/клиентом Finance OS, его state machine не подходит для аренды.
**Решение:** (1) `LeaseContract` — отдельная сущность MDS Property: unit, owner, occupant (имя/компания, контакты — PII), type LTR/STR/OWNER_USE, даты, rent/deposit в minor, статус DRAFT → ACTIVE → EXPIRING → TERMINATED (+ RENEWED через новый договор). Активация проставляет на юните occupancy/rentalMode/leaseStatus/occupantName/leaseEndsAt/monthlyRent; расторжение возвращает VACANT c vacantSince. Один активный договор на юнит (partial unique). (2) `Deal` — сделка CRM: stage по воронке blueprint §6 (NEW → QUALIFIED → PROPERTY_SELECTED → VIEWING → OFFER → NEGOTIATION → LOI → CONTRACT → MOVE_IN → WON | LOST), contact (PII), source/utm, demand (бюджет, площадь, назначение, срок), выбранный юнит + альтернативы, менеджер, nextAction/nextActionAt, rate/terms, lossReason (структурированный). `Unit.commercialStatus` становится производным от самой продвинутой активной сделки (VIEWING→VIEWING, OFFER/NEGOTIATION→NEGOTIATION, LOI→LOI, CONTRACT/MOVE_IN→CONTRACTED; резерв — явный флаг сделки) и пересчитывается сервисом при каждом изменении сделки; ручная смена commercialStatus остаётся для юнитов без сделок. (3) Категории выручки для CEO: потенциальная (все активные), ожидаемая (× вероятность стадии, таблица в core), подтверждённая (CONTRACT+ и депозит). (4) События: таблица `DomainEvent` (outbox) c типом, объектом, payload без PII; воркер доставляет в NotificationAdapter (Telegram) и помечает delivered. Realtime в UI — позже. (5) HTTP API: `/api/property/public/inventory` — опубликованные юниты без PII по slug тенанта c API-ключом тенанта (таблица `ApiKey`, sha256 хэш, scope). Остальной API — после стабилизации сервисного контракта.
**Последствия:** `changeUnitStatus` запрещает ручную смену occupancy/leaseStatus при наличии активного LeaseContract (источник истины — договор) и commercialStatus при наличии активной сделки. Seed Phase P дополняется договорами и сделками. Blueprint §17 «бонус продажника» — после положения о бонусах.

## ADR-019: WorkBot действует от имени сотрудника; ИИ только предлагает черновик
**Дата:** 2026-09-18 · **Фаза/задача:** P-12
**Контекст:** Blueprint §1.9/§7 требует голосового/текстового ввода через Telegram c цепочкой draft → preview → confirm → commit → audit и запрещает ИИ напрямую менять договоры, деньги и ownership. Реальных LLM-API в проекте нет (docs/07: адаптеры + mock).

(2) Бот не имеет собственных прав: API-ключ тенанта (scope WORKBOT) определяет tenant, `telegramChatId` — сотрудника c ролью; черновик и подтверждение выполняются в его TenantContext, audit пишет его как актора. (3) Подтверждение требует права на само действие (таблица `CONFIRM_PERMISSION`) и выполняется только существующими сервисами — ни один guard (BR-P04/P10/P11/P24) обойти нельзя; отказ правила фиксируется как FAILED c кодом (BR-P30). (4) Исходный текст сообщения (может содержать имена/телефоны) хранится в черновике, но не попадает в audit.
**Последствия:** голос и фото — вход в тот же extractor после speech-to-text/классификации (Wave 3b); новые виды действий добавляются парой «intent + CONFIRM_PERMISSION + ветка commit» без изменения API.

## ADR-020: Услуги — слой спроса и качества; деньги считаются по виду исполнителя, цена фиксируется в заказе
**Дата:** 2026-09-19 · **Фаза/задача:** P-16
**Контекст:** Blueprint §12 задаёт Services marketplace как цепочку order → partner/own ops → status → QA → GMV/revenue attribution и требует, чтобы собственный клининг учитывался как выручка/затраты Operations, а партнёрские услуги — как комиссионная монетизация. Платёжного адаптера нет (docs/07), поэтому «оплата» вне системы.
**Решение:** (1) Каталог услуг — справочник тенанта c видом исполнителя: OWN_OPS (вся сумма — выручка эксплуатации) или PARTNER (платформе комиссия в базисных пунктах, партнёру остаток). (2) Заказ хранит снимок цены, комиссии и партнёра на момент оформления (BR-P35): смена каталога не переписывает историю и отчётность. (3) В GMV и выручку попадают только заказы DONE/VERIFIED (BR-P36); открытые и отменённые не считаются; оценка заказчика и SLA-доля — по тем же закрытым заказам. (4) QA заказов повторяет правило заявок (BR-P32): подтверждение (фото/акт) и другой человек. (5) Собственник заказывает через `owner.request` только по своим юнитам и оценивает только свои заказы (BR-P33); заказы через API/бот идут теми же сервисами. (6) Документы по договорам — существующий реестр `Document` (objectType lease_contract/unit); собственник загружает без права `document.upload` через `storeDocument` после проверки владения, чтобы не расширять роль PROPERTY_OWNER на чужие объекты.
**Последствия:** выставление счёта за услугу (AR) и выплата партнёру (AP через Finance OS) — следующий шаг тем же снимком сумм; платёжный адаптер подключается без изменения модели; реестр партнёров как Vendor — когда появится реальная выплата.

## ADR-021: Дебиторка ORDO — только по деньгам, которые ORDO собирает; оплата признаётся только банком
**Дата:** 2026-09-19 · **Фаза/задача:** P-18
**Контекст:** Бизнес-модель Tower (§2.1) разделяет брокеридж (LTR, офисы: комиссия 50% месяца c арендатора, управления после сделки нет) и управление (STR, пулы девелопера, помещения ТРЦ по ДДУ: регулярный % от собранной аренды). При брокеридже аренда идёт собственнику напрямую, и ORDO её не видит. Одновременно non-negotiable №6 Finance OS запрещает статус PAID из UI.
**Решение:** (1) Начисления аренды ведутся только по юнитам под управлением (`managedByPlatform`), иначе дебиторка в системе была бы фиктивной. (2) Начисление — месяц вперёд c пропорцией по дням; оплата признаётся исключительно зачётом входящей банковской транзакции; при разной валюте сумма зачёта вводится в валюте начисления (курс ЦБ подключается адаптером позже). (3) Прекращение договора списывает будущие периоды, текущий остаётся к оплате. (4) Тот же механизм (начисление → поступление → просрочка → собираемость) станет основой для комиссий ORDO (P-14), взносов на содержание (Operations, контур 1) и fee ТРЦ (Mall): обобщение в единый биллинг c видами начислений — следующий шаг, а не переписывание.
**Последствия:** выписка собственника по брокериджу показывает «напрямую вам» вместо суммы; выплата собственнику (payout) по управляемым юнитам появится как отдельный поток, когда будут правила STR/ДДУ; список должников готов для enforcement-механики 2026 (Operations).

## ADR-022: Комиссия ORDO — по продукту сделки; бонус продажника — доля чистой комиссии и только после поступления денег
**Дата:** 2026-09-19 · **Фаза/задача:** P-14
**Контекст:** Бизнес-модель Tower (§2.1–2.2) фиксирует монетизацию по продуктам: аренда — 50% месяца c арендатора (брокеридж), продажа — 3% → 2% → 1,5% c продавца, STR — % от базы (OPEN), паркинг — 50% месяца c собственника; Mall — success fee OPEN. Владелец 19.09.2026 решил: продажник получает 20% комиссии за аренду и +10% при выполнении KPI-чек-листа (онбординг, ключи доступа, интернет, клининг, передача в Services); при продаже ORDO получает 3%, продажник 1% от суммы; STR не решён.
**Решение:** (1) Правило комиссии — справочник в ядре по продукту сделки; ставка переопределяется только внутри коридора; продукты c неутверждённой ставкой выигрываются без комиссии, а не c выдуманной. (2) Комиссия начисляется на WON и признаётся полученной только банковской транзакцией — та же дисциплина, что для платежей и аренды. (3) База бонуса — чистая комиссия после доли внешнего брокера; бонус за продажу задан как доля комиссии (3333 б.п. ≈ 1% от суммы при 3%), чтобы при снижении ставки в коридоре бонус снижался пропорционально, а не превышал треть дохода ORDO. (4) Бонус становится «к выплате» только после полного поступления комиссии; KPI подтверждает не продажник и в срок 14 дней; отмена комиссии до поступления удерживает бонус; выплаченное не отзывается. (5) Выплата — отметка финансов по ведомости c отчётом за период; проводка в зарплату остаётся вне системы до решения о PayrollRun.
**Последствия:** ставки и сроки — настройки тенанта (`bonus_*`), правила STR/ТРЦ подключаются заменой null в справочнике; отчёт бонусов — источник для бухгалтерии; при появлении реального разделения между брокером и менеджером в одной сделке добавится таблица участников c долями.

## ADR-023: Mall — мандат ДДУ включает управление, проценты OPEN не публикуются, линии актива отделены от денег собственников
**Дата:** 2026-09-19 · **Фаза/задача:** P-19
**Контекст:** Бизнес-модель Mall v1.1: гибридная модель (небольшое регулярное вознаграждение c собранной аренды контролируемой базы + комиссии за сделки + линии актива 100% ORDO по конструкции C); размер вознаграждения и success fee — OPEN до тройной сверки; собственникам проценты не озвучиваются; линии актива считаются, но наружу не коммуницируются до соглашения c Piramit Global и правового аудита общих зон.
**Решение:** (1) Мандат — отдельная сущность c жизненным циклом, а не флаг: ACTIVE делает помещение управляемым и включает сбор аренды через ORDO (та же дебиторка, что P-18) — так контролируемая база считается из фактов, а не из справочника. (2) Ставка и success fee — nullable; вознаграждение считается только по утверждённой ставке, а собственник видит проценты только при явной публикации (BR-P46) — прямое исполнение правила «цифры не выходят наружу до сверки». (3) Линии актива (медиа, островки, паркинг, партнёрства) — отдельные объекты c договорами; их выручка не смешивается c деньгами собственников и фондами. (4) Экономика собственника «c ORDO / без ORDO» — функция ядра c тестом, чтобы KSP получал цифры c цепочкой вывода из тех же вводных, что в модели §9.
**Последствия:** фонды OPEX и маркетинг ТРЦ, отчёт собственнику ТРЦ по трафику и маркетинг-фонду, вознаграждение за управление маркетингом — следующий шаг вместе c контурами денег Operations (общая конструкция «целевой фонд»); разделение комиссии c внешним брокером уже учтено в сделках (P-14).

## ADR-024: Services — выручка только по условиям направления, GMV — метрика спроса, cost-to-serve собирается c первого заказа
**Дата:** 2026-09-19 · **Фаза/задача:** P-20
**Контекст:** Бизнес-модель Services v1.0: единой комиссии нет (условия индивидуальны по направлению: комиссия c заказа, регулярный referral как у CityNet, пакеты), Services физически не исполняет, GMV ≠ Revenue, центральная метрика — Contribution = Revenue − Cost-to-Serve, гейт H1A невозможно пройти без данных о стоимости обслуживания; transfer pricing между Services и Operations не определён до Master Model; арендаторы Mall — не клиенты Services.
**Решение:** (1) Каждый заказ хранит снимок трёх уровней — GMV, выручка Services, выручка исполнителя — по условиям направления на момент заказа; для собственной эксплуатации внутренняя ставка Services nullable и до решения считается нулём (честнее нуля ничего нет). (2) Скидка клиенту хранится отдельно и уменьшает цену, а не выручку. (3) Cost-to-serve и жалобы фиксируются по заказу участниками (минуты координации); стоимость часа — настройка тенанта c пометкой «гипотеза». (4) Referral-выручка приходит отчётом партнёра (CSV, идемпотентно), а не заказами; пакет — регулярная покупка конкретной услуги c генерацией заказов джобом. (5) Заказы по юнитам ТРЦ блокируются, кроме услуг c явным флагом для Mall.
**Последствия:** аналитика валидации (penetration, attach rate, повторные, contribution по направлениям) строится из тех же снимков; когда Master Model задаст внутренний тариф, достаточно заполнить ownOpsFeeBp — история не пересчитывается; получение referral-вознаграждения по банку и выставление счёта партнёру — следующий шаг через существующий зачёт транзакций.

## ADR-025: Деньги дома — отдельный фонд и счёт, взносы по кадастру, PAID только банком, вознаграждение ORDO строкой (ставка OPEN)
**Дата:** 2026-09-19 · **Фаза/задача:** P-21
**Контекст:** Бизнес-модель Operations v1.0 и ЗРУ-581: деньги собственников на содержание общего имущества — не выручка управляющей организации; ст. 16 требует годового перерасчёта, ст. 28 — письменного договора c каждым собственником, ст. 29 — ежемесячной отчётности. Размер вознаграждения ORDO не определён до заключения Quantum Law; кадастровые площади внесены не по всем помещениям; часть помещений без установленного собственника.
**Решение:** (1) `HouseFund` c отдельным банковским счётом; поступления на счёт ORDO во взносы не зачитываются (WRONG_ACCOUNT). (2) Взнос = кадастровая площадь × тариф; до внесения кадастра — договорная площадь c флагом `preCadastre`, пересчёт со следующего месяца после внесения (прошлые начисления не пересчитываются). (3) Статус PAID — только зачётом банковской транзакции, как и для аренды (BR-P37); частичные оплаты → PARTIAL. (4) Вознаграждение ORDO — расчётная строка `managementFeeLine(собрано, ставка)`; при `managementFeeBp = null` строка не публикуется и в отчёте собственникам показывается «ставка не зафиксирована»; ставку задаёт house.manage после заключения. (5) Годовой перерасчёт — расчётный (`annualRecalc`), без автоматических проводок; кредит/недобор показывается на дашборде и в отчёте, применение — решение собрания. (6) Расход из денег дома всегда c подрядчиком, статьёй и описанием; без документа/заявки помечается «без подтверждения» — не блокируется (данные приходят из 1С и бумажных актов), но виден в отчёте. (7) Enforcement (пени, ограничение услуг) не реализуется — только список должников и задача Operations.
**Последствия:** отчёт собственникам можно публиковать без фиксации ставки; при внесении кадастра сумма взноса меняется только на будущие периоды — расхождения прошлых месяцев решаются перерасчётом по году; для «Мониторинга платежей» и авто-зачёта нужен импорт выписки по счёту дома (adapter bank — тот же формат, что и для счёта ORDO).

## ADR-026: Родные выгрузки 1С/Didox импортируются как есть; ПИНФЛ и оклады не читаются; второй счёт — UNVERIFIED; аванс из ОСВ = задача на закрывающие

## ADR-027: Налоговый профиль ORDO — налог c оборота 4%, ЕСП 12%, НДФЛ 12% (ИНПС 0,1% внутри), срок 15 число; оценка из ФОТ и выручки
**Дата:** 2026-09-19 · **Фаза/задача:** H-10
**Контекст:** Бухгалтерия (19.09.2026): ORDO на налоге c оборота 4%; ЕСП 12% от ФОТ; НДФЛ 12% от ФОТ; ИНПС 0,1% от ФОТ удерживается из НДФЛ; всё платится до 15 числа ежемесячно. 1С:Бухгалтерия для Узбекистана ред. 3.0 работает в облаке Clobus (интеграция c банком, входящие СФ из Didox), подписка оформлена на Palym Group до декабря.

**Последствия:** ожидаемые суммы налогов появляются автоматически после утверждения ведомости и выставления счетов; расчёт бухгалтерии вне коридора ±10% создаёт задачу проверки, а не блок; смена ставок — правка правила c audit.

## ADR-028: CRM Tower — контакт как единица клиента; автопривязка по телефону; PII по праву; слияние вместо удаления
**Дата:** 2026-09-19 · **Фаза/задача:** P-22a
**Контекст:** Сделки хранили клиента строкой (имя/телефон/email), один человек появлялся в нескольких сделках и лидах под разным написанием; клиентской базы как таковой не было. Владелец приоритезировал CRM и рабочий контур Tower.

## ADR-029: Воронка собственников как вторая CRM-воронка Tower; расчёт трёх сценариев — обязательный шаг; STR fee OPEN
**Дата:** 2026-09-19 · **Фаза/задача:** P-22b
**Контекст:** Бизнес-модель Tower: рост через захват фонда и конверсию собственников (H4), правило «собственнику всегда показываем расчёт STR / mid-term / LTR и продаём STR только когда он выгоден собственнику»; ставка STR fee до валидации не определена; % за управление берётся только в STR и ТРЦ (решение владельца).
**Решение:** (1) Воронка живёт на `PropertyOwner` (стадия, следующее действие, менеджер, источник, причина отказа), а не отдельной сущностью «сделка c собственником» — один собственник ведётся один раз, помещения и договор управления уже на нём. (2) Стадии синхронизируют факты (согласие, статус договора ст. 28, «под управлением» только при реальном managedByPlatform), чтобы воронка не расходилась c реестром. (3) Расчёт: LTR/mid-term без вознаграждения c собственника (комиссия c арендатора, BR-P41), STR — за вычетом opex и ставки ORDO из `tenant.settings.owner_calc.str_fee_bp`; пока null — иллюстративная ставка c пометкой и `provisional` рекомендацией; параметры (загрузка, opex, множители, простой) — настройки тенанта, переопределяемые в форме. (4) Показ расчёта — отдельный факт (`calcShownAt`), воронка подсвечивает, где он не сделан. (5) Активности собственника — тот же `UnitActivity` c `ownerId` (единая история c юнитами и сделками). (6) Конверсия считается по сегментам помещений (для валидации H4), а не по сумме.
**Последствия:** команда ведёт собственников как воронку c просрочками и напоминаниями; после фиксации STR fee достаточно одной настройки; расчёт — иллюстрация, не оферта: юридические формулировки договора управления вне системы.

## ADR-030: CRM Tower как путь сотрудника — бот и мобильный «Мой день» первичны, web-экраны вторичны; роль CALL_CENTER; телефония через адаптер
**Дата:** 2026-09-19 · **Фаза/задача:** P-23…P-27 (docs/21)
**Контекст:** Команда Tower — один продажник и один сотрудник колл-центра, работают c телефона; владелец требует CRM как путь сотрудника, мобильную версию, Telegram-бота и аналитику «слушать всё».

## ADR-031: Публичный доступ к серверу — только HTTPS; без домена используем sslip.io + Caddy; демо-тенант Tower живёт на проде отдельно от реальных данных
**Дата:** 2026-09-19 · **Фаза/задача:** H-11
**Контекст:** Сервер DigitalOcean развёрнут (H-06), но 15.09 внешний вход закрыт: реальные финансовые данные Rooftop по HTTP не гоняем, а домена у продукта пока нет. Владелец хочет кликать CRM Tower на реальном сервере уже сейчас, до покупки домена и до реальных данных по башне.

(2) Имя хоста без домена — `<ip-через-дефисы>.sslip.io`: публичный wildcard-DNS резолвит его в IP, Let's Encrypt выдаёт обычный сертификат; при появлении домена меняется один секрет `PUBLIC_HOST`. Реальные данные Rooftop и синтетика не смешиваются — tenant isolation (контроль 11).
**Последствия:** прод доступен c телефона по HTTPS без затрат на домен; сертификат для IP-имени — временное решение, домен остаётся задачей владельца; повторный деплой не трогает уже привязанные Telegram-чаты и пароли; если в демо-тенант начнут вносить реальные данные Tower — заводится отдельный реальный тенант, демо не переиспользуется.

## ADR-032: Телефония Tower — OnlinePBX; мессенджер c клиентами — Telegram, WhatsApp без интеграции; адаптер c настраиваемой картой полей и диагностикой
**Дата:** 2026-09-19 · **Фаза/задача:** P-29
**Контекст:** Владелец назвал провайдера: OnlinePBX; для сообщений c клиентами используется Telegram, WhatsApp — очень редко. Официальная документация формата webhook OnlinePBX из среды разработки недоступна (сетевая политика), а CLAUDE.md запрещает жёстко зашивать предположения о форматах внешних систем.
**Решение:** (1) `OnlinePbxAdapter` принимает form-urlencoded и JSON, поля ищет по карте кандидатов (по умолчанию CDR-имена FreeSWITCH — основы OnlinePBX), карта, зона АТС и длина внутренних номеров настраиваются на тенанте; промежуточные события («Ответили») игнорируются, пропущенный определяется по событию или причине завершения при нулевой длительности. (2) Каждый webhook отмечается временем; непонятое тело сохраняет только ключи (значения — персональные данные — не хранятся): карта полей уточняется по первому реальному звонку без правки кода. (3) Аутентификация — API-ключ TELEPHONY в заголовке или `?key=`, если АТС не умеет заголовки. (4) Мессенджеры: интеграций c Telegram-чатами клиентов и WhatsApp не делаем — сотрудник пересылает сообщение рабочему боту (принцип «не читаем чужие чаты», ADR-030); источник лида WHATSAPP добавлен, чтобы аналитика по каналам была честной.
**Последствия:** подключение OnlinePBX — настройка в кабинете АТС и на экране «Телефония», без деплоя; первый звонок может лечь в диагностику, после уточнения карты всё последующее пишется автоматически; переход на другого провайдера — новый адаптер без изменения домена; телефония 1С/Clobus и записи разговоров не затрагиваются.

## ADR-033: Порядок внедрения — сначала ORDO (коммерция → сервис → операции), затем адаптация под Rooftop и Sense48; данные клиентов не смешиваются
**Дата:** 2026-09-19 · **Фаза/задача:** P-30
**Контекст:** Владелец подтвердил фокус: всё текущее делается для ORDO (управляющая компания объекта Piramit: Tower, Business Center, Mall). (3) Финансовый модуль для ORDO — тот же Finance OS в тенанте `ordo` (импорт 1С/Didox уже проверен на реальных выгрузках ORDO), отдельного продукта нет.

## ADR-034: Кадастровая площадь — источник истины для взносов и цены; проектная и договорная хранятся рядом как справочные

**Контекст:** Владелец зафиксировал правила загрузки реестра Piramit Tower (файлы Довлета — кадастр и продажи, Озде — Mall). Импортируем не выборку, а весь объект; у помещения четыре разных вопроса, которые нельзя сворачивать в один статус.
**Решение:** (1) Импортируем **весь реестр Tower**, а не только свободные помещения: квартиры 18–47, офисы 2–17, паркинг, кладовые, Mall; сохранённые/проблемные/судебные помещения тоже, со своим статусом. (2) У каждого помещения **четыре независимые оси статуса**: владение (кто собственник + статус кадастра/тапу: передан / ждёт выдачи / у компании / бартер / проблемный / судебный), использование (свободно/занято — `occupancy`), аренда (`rentalMode` + `leaseStatus` + ставка), продажа (`commercialStatus` + цена). Оси не смешиваются: помещение может быть «продано и передан кадастр» по владению, «занято» по использованию и «не в аренде» одновременно. (3) **Квартиры и офисы грузим полностью**, но записи собственников с контактами создаём **только после сверки исходного файла и дедупликации** по телефону и имени (BR-P55): сначала реестр помещений и обезличенные статусы, отдельным шагом — контакты. (4) **Паркинг (729) и кладовые (371) — полноценные объекты** общего реестра c типами PARKING и STORAGE, не отдельный список; у них те же четыре оси. (5) Площади — по ADR-034 (кадастр главный).
**Последствия:** в модель Unit добавляются ось владения — enum статуса кадастра/владения (`tenureStatus`) — и связь помещения c продажей; импортёр Довлета грузит помещения и статусы владения/кадастра без контактов, второй проход создаёт собственников после дедупликации; коммерческая команда видит по каждому помещению отдельно, кому принадлежит, кем занято, сдаётся ли и продаётся ли.

## ADR-036: Пользовательское имя платформы — DMS (замена «Finance OS» в UI); технические идентификаторы (@finance-os/*, БД finance_os) переименовываются отдельно (P-09)
**Дата:** 2026-09-19 · **Фаза/задача:** P-32
**Контекст:** Владелец задал рабочее название всей платформы — **DMS** — и попросил заменить пользовательские упоминания «Finance OS» на DMS. Архитектура остаётся multi-tenant: DMS — продукт, ORDO — тенант/клиент, Piramit Tower — объект внутри ORDO; ни один клиент не хардкодится как владелец платформы. Ранее ADR-016 фиксировал бренд «MDS» и «Finance OS» как имя финансового модуля. Владелец подтвердил (не опечатка): единое пользовательское имя продукта — **DMS**; «MDS», «MDS Property», «Finance OS» в пользовательской части не оставляем, чтобы не было трёх имён сразу.
**Решение:** (1) Пользовательские места переименованы в **DMS** (из «Finance OS», «MDS», «MDS Property»): заголовок приложения и вкладки, PWA-манифест (name/short_name) и apple-web-app title, экран входа, сайдбар и подписи разделов, подсказки экрана миграции (`apps/web/app/layout.tsx`, `apps/web/public/manifest.webmanifest`, `apps/web/messages/ru.json`), тема письма-уведомления и имя отправителя уведомления, README, e2e-проверка заголовка. (2) `Property Assistant` (Telegram-бот) — отдельное имя интерфейса, не переименовывается. (3) Названия тенантов и объектов остаются данными (`tenant.legalName`, `unit`/building), не бизнес-логикой; DMS/ORDO/Piramit не зашиты в код. (4) Технические идентификаторы **не трогаем автоматически** — список в README/этом ADR: workspace-scope `@finance-os/*` (сотни импортов), имя БД `finance_os` (`DATABASE_URL`, `docker-compose.prod.yml`), сервис/проект docker, поле «Отправитель» в файле обмена 1С (`clientBankExchange.ts`), внутренние спец-доки (`CLAUDE.md`, `docs/01/13/16/17`, `MASTER_PROMPT.md`, история `DECISIONS.md`), dev-логи seed. «MDS» как технический/данные-идентификатор пока оставлен и внесён в список: значение `tenant.settings.product = 'MDS Property'` (данные, не отображается), комментарии в исходниках и заголовки спец-доков (`docs/20`, `MASTER_PROMPT`, `CLAUDE.md`), товарный знак «MDS»/«Finance OS» в `LICENSE` и `docs/17-ip-ownership.md` (правовой документ — меняется только через юриста/ADR, IP-01). Их переименование — отдельная задача P-09 (репозиторий + scope + БД), git-история сохраняется.
**Последствия:** пользователь видит «DMS»; внутренние имена модулей остаются в спецификации; смена scope пакетов и имени БД делается одним запланированным шагом с миграцией, чтобы не сломать импорты, прод-БД и обмен с 1С.

## ADR-037: Геймификация — тонкий слой поверх бизнес-фактов, конфиг-правила, XP выводится (не начисляется кликами)
**Дата:** 2026-09-20 · **Фаза/задача:** этап DMS core daily experience (ТЗ §13-20)
**Контекст:** Нужна лёгкая геймификация (XP, уровни, streak, 3 миссии, награды) для молодой команды, но без параллельного мира и без XP за «клики», которые легко накрутить. Требование: пороги/миссии/награды меняются конфигом, не переписыванием CRM.
**Решение:** (1) XP/уровень/streak/миссии **вычисляются из уже зафиксированных бизнес-фактов** (`UnitActivity` по `actorId`, `Deal` по `managerId`), а не пишутся отдельным потоком. Идемпотентность — по построению: каждый факт-строка учитывается один раз, повторное чтение состояния ничего не удваивает. (2) Все правила — единый конфиг в `packages/core/src/gamification` (XP_RULES, LEVELS, миссии по ролям, STREAK_MIN_XP), чтобы менять без правки CRM-логики. (3) Уровни — recognition, НЕ права (доступ только через RBAC). (4) Единственная персистентная часть — заявки на награды (`RewardRedemption`), каталог из `tenant.settings.rewards` (дефолт в коде). (5) Изоляция tenant/role — запросы состояния всегда по `tenantId`+`userId`, миссии по ролям из `ctx.roles`.

**Уточнение 2026-09-22 (обратная связь владельца):** XP даётся только за РЕЗУЛЬТАТ, не за попытку и не за клик. (a) За сам звонок XP убран — звонок остаётся фактом (и метрикой миссии `leads_handled`), но не начисляет очков; засчитываются follow-up, проведённый показ, оффер, закрытая сделка. (b) Миссия «передать N квалифицированных лидов» убрана: передача — служебный шаг, а не цель дня; превращать её в KPI значит поощрять сброс сырых лидов менеджеру ради галочки. У КЦ остаётся 2 миссии (обработать лиды, закрыть follow-up). (c) `STREAK_MIN_XP` (30) намеренно выше одного follow-up: день в streak — это день с реальной отдачей, а не присутствие/активность вхолостую. (d) Геймификация — не инструмент управления людьми: владелец видит факты и нагрузку команды, а не «очки» сотрудников. Неиспользуемые события (`CALL_LOGGED`, `VIEWING_SCHEDULED`, `LEAD_QUALIFIED`) и метрика `handoffs` удалены как мёртвый код.
**Последствия:** нет двойного учёта, накрутки и стимула к «активности вхолостую»; пороги и миссии тюнятся конфигом; метрика `leads_handled` — прокси по активностям (провизорно); при желании точного «показ проведён»/«лид квалифицирован» позже добавляется явный маркер активности/стадии без смены архитектуры.

## ADR-038: Роли COMMERCIAL_DIRECTOR (Kamila) и CEO как операционные профили
**Дата:** 2026-09-22 · **Фаза/задача:** DMS operating profiles (запрос владельца)
**Контекст:** Владелец попросил завести Kamila (коммерческий директор) и CEO как отдельные операционные профили. В матрице прав было 13 ролей; этих двух не было, из-за чего роль-ориентированные профили из прототипа нельзя «оживить» в приложении. CEO при этом должен быть exception-first и в основном смотрящим, а система имеет строгие финансовые контроли (four-eyes, PAID только из банка), которые нельзя случайно ослабить новой ролью.
**Решение:** Добавлены две роли в `ROLE_CODES` (core) и в enum `RoleCode` (Prisma, миграция `20260919180000_roles_director_ceo`). (1) **COMMERCIAL_DIRECTOR** на уровне матрицы = точная копия грантов `COMMERCIAL_MANAGER` (надзор над коммерцией). Отличие «видит всю команду» — это область ВИДИМОСТИ, решается доменной логикой (как `seesAll` в getMyDay), а не матрицей прав (матрица область-видимости не выражает — см. её шапку). (2) **CEO** получает ТОЛЬКО видимость: все `*.view` + `dashboard.owner`/`dashboard.ops` + `audit.view` + `owner.pipeline`. Ни одного права на создание/изменение/согласование/управление — CEO физически не может подготовить платёж, согласовать батч/PR, изменить контракт, поставить PAID или управлять людьми. Инвариант зафиксирован тестами (`rbac.test.ts`): «CEO разрешено ⊆ набор чтения» и явный deny по контрольным правам; отдельный тест «director == manager». Роль CEO не равна OWNER: у владельца есть права согласования, у CEO — нет.
**Последствия (ADR-038):** профили из прототипа теперь можно собрать на реальных ролях; four-eyes и финансовые контроли неизменны (CEO вне мутаций по построению и по тесту); при добавлении ролей rbac-тест (data-driven по `ROLE_CODES`×`PERMISSION_MATRIX`) валидирует их автоматически. Открытый вопрос на потом: роль-ориентированная НАВИГАЦИЯ (сейчас меню одно на всех, режется правами — CEO с широким чтением увидит много пунктов; это исправляется отдельной задачей сборки меню под профиль, не матрицей). Человеко-читаемые подписи ролей в админке пока не заведены (все роли показываются кодом — единообразно).


## ADR-039: Role-based navigation — группировка разделов + компактный «фокус» для узких ролей
**Дата:** 2026-09-22 · **Фаза/задача:** DMS упрощение (ночной проход)
**Контекст:** Единое плоское меню из 44 пунктов, отфильтрованное по правам, — главная причина ощущения «сложно»: узкая роль (колл-центр, аренда) видела десятки нерелевантных строк, меню без группировки, нижнее меню на телефоне жёстко зашито 5 пунктами для всех.
**Решение:** Презентационный слой поверх той же матрицы прав (доступ НЕ меняется). (1) У каждого пункта меню есть `section` (daily/commercial/property/finance/reports/admin); меню рендерится сгруппированно с заголовками. (2) Роли с узким операционным контуром (`FOCUSED_ROLES`: CALL_CENTER, COMMERCIAL_MANAGER, BROKER, COMMERCIAL_DIRECTOR, OPERATIONS_MANAGER, MARKETING, PROPERTY_OWNER, CEO) получают компактный блок «Главное» (`PRIMARY_NAV` по роли) + сворачиваемые `<details>` «Все разделы» с полным сгруппированным списком. Пользователь с любой широкой ролью (владелец/финансы/админ) видит сгруппированные разделы сразу, без «фокуса». (3) Нижнее меню на телефоне — из фокус-набора роли (или запасной набор), а не жёстко зашитые 5 пунктов. Всё серверно, без клиентского JS (нативный `<details>`).
**Последствия:** узкая роль видит 3–5 пунктов вместо 44, ничего не теряя (полный список за один клик); права остаются единственным источником доступа (каждый пункт по-прежнему `can()`-фильтруется, что подтверждено e2e для focused и broad ролей). Открытый вопрос: `PRIMARY_NAV` — разумные умолчания, тюнятся по обратной связи; человеко-читаемые подписи ролей (не кодом) — отдельная задача.


## ADR-040: Tower SPEC v1.0 — COMMERCIAL_MANAGER как deprecated-алиас BROKER; фиче-флаги; settings-таблица для порогов/ставок (Phase 1)
**Дата:** 2026-09-20 · **Фаза/задача:** Tower Phase 1 (реализация утверждённого SPEC v1.0, пакет ORDO_Tower_Spec)
**Контекст:** Владелец утвердил операционную модель Tower (SPEC.md v1.0 + вайрфреймы umar/aziz/kamila/ceo). SPEC консолидирует роли до четырёх (CALL_CENTER, BROKER, COMMERCIAL_DIRECTOR, CEO), сливая COMMERCIAL_MANAGER в BROKER (§1). Требования: STR и ТРЦ (MALL) — за фиче-флагами (§0/§9); пороги алертов (§7) и ставки комиссий (§4) — настройки, не константы. Условие владельца на Phase 1: ничего необратимого — CM оформить алиасом, НЕ миграцией; жёсткий мёрж и расширение прав BROKER до полного цикла — отдельной задачей (Phase 2).
**Решение (Phase 1, только обратимый код, без миграций):**
1. **CM ⇒ BROKER — однонаправленный deprecated-алиас** (`ROLE_ALIASES` в core/context, `expandRoles`). Контекст с COMMERCIAL_MANAGER дополнительно распознаётся как BROKER для `can()`/`hasRole()`. Права BROKER НЕ расширяются: т.к. в текущей матрице BROKER ⊆ COMMERCIAL_MANAGER, для `can()` это no-op и не ломает существующие доменные правила, где брокер намеренно ýже менеджера (кап LOI и т.п.). Живых пользователей-CM нет (только сид). Откат — очистить `ROLE_ALIASES`. Двунаправленную эквивалентность сознательно НЕ делаем: она сняла бы каповые правила брокера, которые SPEC переопределяет только в Phase 2 (§3.1/§2.2).
2. **Фиче-флаги** (`core/config/features.ts`): `FEATURE_STR`, `FEATURE_MALL`, `FEATURE_POOL_COMMISSIONS` — дефолты выключены (STR/ТРЦ на паузе, пулы — гипотеза). Чтение из env с безопасным дефолтом, браузеро-безопасно.
3. **Настройки Tower** (`core/config/towerSettings.ts`): пороги §7 как типизированные дефолты (`TOWER_THRESHOLD_DEFAULTS`, `towerThresholdsFrom`) — раньше их в коде не было. Пул-комиссии девелопера (§4 HYPOTHESIS) — `poolManagementCommissionMinor`, 15%, только при `FEATURE_POOL_COMMISSIONS`. Ставки/правила комиссий §4 (LTR/офис 50%, продажа 3% коридор 1.5–3%, STR/ТРЦ OPEN) **уже есть** в `property/commission.ts` — НЕ дублируем; тест подтверждает соответствие SPEC §4. `ApprovalPolicy` НЕ расширяем — остаётся для аппрувов/four-eyes (включая утверждение % в коридоре); settings-ТАБЛИЦА (миграция) и enum `DUE_DILIGENCE` — в Phase 2 (требуют миграций, отложены по условию обратимости).
**Последствия:** роль-модель приведена к SPEC обратимо, без миграции и без регрессий (полный прогон: только 2 пре-существующих date-sensitive теста my-day падают и на baseline — не связаны с изменением); STR/ТРЦ/пулы гейтятся флагами; пороги и пул-ставка тюнятся из одного места. Phase 2: воронка §3.1 + экран CALL_CENTER «Очередь входящих», расширение BROKER до полного цикла и SoD денег (§2.2), settings-таблица, `DUE_DILIGENCE` как гейт перед CONTRACT.
