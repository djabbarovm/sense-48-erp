## Модель времени

Все *_at из amoCRM — epoch-секунды в UTC. occurred_at = реальное время события; source_updated_at = последнее изменение записи в amoCRM; synced_at = время выгрузки этим экстрактом.

## Провенанс

Каждая сделка помечена provenance_source=AMOCRM, несёт внешние id (lead_id, pipeline_id, source_stage_id), source-время (created_at/updated_at/closed_at) и synced_at (время этой выгрузки). Исходные стадии amoCRM сохранены как source_stage_*; normalized_stage — ОТДЕЛЬНАЯ аналитическая нормализация в стадии DMS, старую историю не переписывает.

## Что надёжно / частично / отсутствует

Лист `AnalyticsReadiness` — матрица: МЕТРИКА → ИСТОЧНИК → ПОКРЫТИЕ% → НАДЁЖНОСТЬ → AVAILABLE/PARTIAL/NOT_AVAILABLE → что DMS обязан собирать с сегодняшнего дня. Ключевое:
- **Кол-во сделок / период** — AVAILABLE (HIGH, покрытие 100%). DMS: created_at фиксируется системой при создании — уже надёжно
- **Конверсия по воронке (стадия→стадия)** — PARTIAL (MEDIUM, покрытие 70.2%). DMS: DMS обязан писать КАЖДЫЙ переход стадии как событие (occurred_at) с сегодняшнего дня
- **Время в стадии / скорость сделки** — PARTIAL (LOW, покрытие 70.2%). DMS: entered_at/exited_at на каждый переход — иначе time-in-stage посчитать нельзя
- **Сумма/стоимость сделки** — PARTIAL (LOW, покрытие 0.8%). DMS: сумма — из подтверждённого финфакта DMS/Finance, не из CRM (CRM = намерение)
- **Атрибуция по сотруднику** — AVAILABLE (MEDIUM, покрытие 100%). DMS: ответственный на момент КАЖДОГО этапа (история смены владельца), не только текущий
- **Источник/канал лида** — AVAILABLE (MEDIUM, покрытие 6%). DMS: структурированный справочник источников + UTM на входящем лиде
- **Причины отказа** — PARTIAL (MEDIUM, покрытие 6.7%). DMS: обязательная причина отказа из справочника при переходе в LOST
- **Активность (звонки/задачи)** — PARTIAL (LOW, покрытие 100%). DMS: активность — вторичный индикатор; связывать с исходом, а не рейтинговать по кол-ву звонков
- **Привязка к объекту (Unit)** — NOT_AVAILABLE (LOW). DMS: DMS должен вести deal.unit_id; авто-матчинг по имени НЕ делаем — нужен маппинг-репорт

## Важные оговорки

- История стадий восстановлена из `/events` — amoCRM хранит события ограниченный срок, поэтому ранние переходы могут отсутствовать (PARTIAL). Мы НЕ симулируем недостающие переходы. DMS должен фиксировать каждый переход как событие с этого момента.
- Суммы сделок берутся из amoCRM (намерение), а НЕ подтверждённый финфакт. Источник истины по деньгам — DMS/Finance.
- Кастом-поля не удалялись до ревью: см. лист `CustomFields` (fill-rate, примеры значений, решение KEEP_RAW/MAP/IGNORE/NEEDS_DECISION).
- Привязка сделок к объектам (Unit) НЕ восстанавливалась авто-матчингом по имени — это отдельный маппинг-репорт (сейчас NOT_AVAILABLE).
